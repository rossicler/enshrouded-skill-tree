# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Enshrouded Skill Planner: a Next.js 16 (pages router, React 19) app for planning and sharing Enshrouded skill-tree builds. It uses Redux Toolkit, Tailwind 4 and next-i18next 16 (`en`, `fr`; import from `next-i18next/pages`). MongoDB is optional; it only backs short share URLs. Node 24 (`.nvmrc`, `engines`), and the package manager is yarn 1 (`yarn.lock`) with workspaces.

The repo root is the site. The skill tree itself (data, rules, build codes, points, stats, skill text and search) is the workspace package `packages/core` (`@enshrouded/core`), so other apps can reuse it. The site imports it by name (`import { SkillNodes } from "@enshrouded/core"`, listed in `transpilePackages`). Core ships TypeScript source (`main: src/index.ts`, no build step) and must stay host-agnostic: relative imports only (never `@/`), no React, no `next/*`, no `window`/`document`, and every external import declared in its own `package.json`. `scripts/package-boundary.test.mjs` enforces this and loads core in a plain Node process, and `yarn typecheck` also type checks core without the DOM library (`packages/core/tsconfig.json`). Run `yarn install` at the root only.

The tree's React UI is the second workspace package, `packages/react` (`@enshrouded/react`, also in `transpilePackages`): the SVG tree view with pan/zoom, tooltips and the click rules. Its entry starts with `"use client"`, React is a peer dependency, and it may use `window`/`document` (the boundary test allows that for this package only; it still bans `@/`, `next/*`, undeclared imports and relative imports that leave the package). Its node art, labels, tooltip art, decorations and sounds live in `packages/react/assets`; `yarn sync-assets` (run by `predev` and `prebuild`) copies them to the gitignored `public/skill-tree/`, served at `/skill-tree` (`SKILL_TREE_ASSETS`). Never add files to `public/skill-tree/` by hand.

## Commands

```bash
yarn dev                                  # dev server on :3000 (predev copies the tree assets)
yarn build                                # prebuild runs validate-translations + generate-version + sync-assets first
yarn sync-assets                          # copy packages/react/assets to public/skill-tree
yarn test                                 # vitest run (packages/*/src/__tests__ and scripts/*.test.mjs)
yarn vitest run packages/core/src/__tests__/nodePosition.test.ts   # single test file
yarn vitest run -t "name substring"       # single test by name
yarn typecheck                            # next typegen + tsc --noEmit, then tsc -p packages/core (no DOM lib)
yarn validate-translations                # check every locale has all text the app shows or searches
yarn import-skills <export.json> [--changes=path] [--apply]  # preview/apply a game import (see below)
yarn e2e                                  # Playwright browser tests (desktop + mobile emulation)
yarn e2e:visual [--update-snapshots]     # screenshot comparison of the main screens (local references)
```

Setting `SKILL_DATA_EXPORT=<path to enshrouded-tools export>` turns on an extra full-source integration test in `scripts/skill-data.test.mjs`.

Env (`.env.local`, see `.env.example`): `BASE_URL`, `MONGODB_URI`, `NEXT_PUBLIC_GOOGLE_ANALYTICS`. `MONGODB_URI` is optional: `src/lib/mongodb.ts` connects lazily via `getMongoClient()`, and without the variable the app runs with DB features off (`/api/code` returns 503). The `dev-no-db` entry in `.claude/launch.json` runs the dev server on port 3001 and assumes no `MONGODB_URI` in `.env.local`.

There is no lint script: Next 16 removed `next lint` and the repo has no ESLint config.

Browser tests (`e2e/`, `playwright.config.ts`) start their own server on port 3101 without `MONGODB_URI` (`yarn dev`, or `next start` on the last build with `PW_SERVER=start`, which CI uses). Run `npx playwright install chromium` once. They use only `data-*` hooks (`data-node-id`, `data-state`, `data-level`, `data-link-*`, `data-skill-tooltip`, `data-action`, `data-hud`, `data-dialog`, ...), never DOM ids or classes, so keep those hooks when changing markup. `positions.spec.ts` checks, within 1px at 1280x800, that every node is drawn where `packages/core/src/constants/gameSkillData.json` puts it and every link joins its two nodes (or a base node and its anchor). Expected positions come from the data, so game imports need no update; only the initial view (scale and tree-center screen position) is pinned in the test. In the SVG renderer `data-node-id` and the other node hooks sit on each node's transparent hit circle, and links are `line[data-link-from][data-link-to][data-link-kind]`. `viewport.spec.ts` pins the wheel speed (17% of the current scale per notch, so 6 notches span the planner's zoom; a trackpad pinch follows the fingers 1:1; `WHEEL_ZOOM_PER_NOTCH` and `PINCH_SPEED` in `packages/react/src/PanZoom.tsx`) and the pan bounds (`PAN_MARGIN` in `packages/react/src/layout.ts`), both tuned by hand.

Styling is Tailwind 4, configured CSS-first in `src/styles/globals.css` (`@theme`: custom colors and the Tailwind 3 values of the default colors in use). It `@import`s `packages/react/theme.css` (the package's own `skill-tree-*` tokens, e.g. the search glow animation) and `@source`s the package, as any host must. There is no `tailwind.config`. Turbopack builds both `dev` and `build`. Every modal uses `GameDialog` from `@enshrouded/react` (Headless UI 2 `Dialog` with `transition`).

## Architecture

### Core package layout (`packages/core/src`)
- `index.ts` is the only entry point; everything public is exported there.
- `constants/`: `gameSkillData.json` (generated), `LegacyNodes.ts` (authored presentation), `Nodes.ts` (`buildSkillTree`, `SkillNodes`, `getMaxLevel`, `RETIRED_NODES`), `Biomes.ts`, `Stats.ts`, `TreeLabels.ts`, `skillTreeVersion.ts`.
- `selection.ts` (unlock/refund rules, `sanitizeSelection`), `actions.ts` (`applySkillAction`: what a primary/secondary click does, as a pure function), `build.ts` (build codes), `points.ts` (points and hard cap), `links.ts` (lines to draw), `text.ts` (skill and tree text), `utils/` (positions, interpolation, text prefix, search, stats).
- `locales/{en,fr}/nodes.json` (per-type skill text) and `locales/{en,fr}/tree.json` (tree labels).

### React package layout (`packages/react`)
- `src/index.ts` (`"use client"`) is the only entry. It exports `SkillTreeProvider` (`locale`, `assetBaseUrl`, `sound`, `hardCap`, `onNotice`), `SkillTreeView`, `SkillTreeCard`, `useSkillBuild`, the points/stats/search hooks and panels, and the UI kit.
- `SkillTreeView` is controlled (`selection` + `onSelectionChange`; without the callback it is read-only). It takes `confirmRefund` (asked before a cascade refund), `highlightedTypes` (search), `initialFocusNodeId`, `getNodeShareUrl`, `initialView` (`"center"`, the planner's fixed zoom, or `"fit"`, the whole tree fitted to the container) and `tooltipStrategy`, fills its container, and exposes `zoomIn`/`zoomOut`/`center`/`focusNode` through its ref. It never shows toasts or dialogs itself: hard cap, out-of-range and copied links go to `onNotice`.
- `layout.ts` computes every position once from core (tree units; nothing is measured from the DOM). `svg/` holds the memoized node and link components, whose props are primitives so one action re-renders only what changed (`__tests__/SkillTreeView.test.tsx` counts renders). Input is delegated from the `<svg>`; one react-tooltip instance serves every node. `PanZoom.tsx` wraps react-zoom-pan-pinch around the `<svg>`.
- The site's `src/pages/card-demo.tsx` (/card-demo) is a 404 unless the server runs `next dev` or has `SKILL_TREE_DEMO_PAGES=1` (set by `playwright.config.ts`), so deployed sites don't serve it.
- `SkillTreeCard.tsx` is the tree in a caller-sized box (360 × 360 for a side the container leaves unsized), built on `SkillTreeView` with `initialView="fit"` and a fixed-position tooltip. The wheel zooms it only while it has focus or with Ctrl, so the page scrolls past it. Its buttons (`CardControls.tsx`) zoom, expand it to an overlay portaled to `<body>` (a second view with the same props; Esc returns focus to the card) or make the card element fullscreen (falling back to the overlay). `readOnly` keeps tooltips. Every listener it adds sits on its own elements, so cards on one page stay independent. `src/pages/card-demo.tsx` (`/card-demo`, not linked) shows cards at several sizes, and `e2e/card.spec.ts` and `e2e/card-mobile.spec.ts` test it.
- `art.ts` picks each node's frame and icon; `glow.ts` the search highlight. `locales/{en,fr}.json` holds the package's own text (tooltip, card, UI kit, panels, search, biome and stat names), read with `uiText`/`useUiText` in the provider's locale and checked by `validate-translations`.
- Points, stats and search: `usePoints(selection, { playerLevel, biomes })`, `useStats(selection, flameLevel)` and `useSkillSearch(query, locale, { exact })` (`hooks.ts`) are thin wrappers over core's `getPointsSummary`, `getTotalStats` and `searchSkills`. The ready-made pieces take values and callbacks as props and hold no store: `PointsPanel` (layout `panel` or `bar`, with `FlameLevelControl` and `BiomeBudgetButton`/`BiomeBudgetDialog`), `StatsList`/`StatsDialog`/`StatsButton`, and `SkillSearch`. The site's HUD (`src/components/hud/`) feeds them from Redux.
- The game-styled UI kit lives in `src/kit/`: `GameButton` (plays the provider's hover sound), `GameButtonGroup`, `GamePanel`, `GameInput`, `GameTooltip`, `CopyInput` and `GameDialog`/`GameDialogTitle`. Images are plain `<img>` from `assetBaseUrl`; decorations show from the `md` breakpoint up, as on the site. `/card-demo`'s last section wires a card to the panels through the hooks (`e2e/card-wired.spec.ts`).
- `scripts/sync-assets.mjs <dest>` copies `assets/` for a host.
- Hosts render the views on the server and hydrate them, so render output must not depend on the JavaScript engine: `layout.ts` rounds every coordinate to 0.001 tree units, because `Math.sin`/`Math.cos` can differ in the last bit between Node and the browser (a hydration mismatch otherwise).

The site wires it up in `src/components/SkillPlanner.tsx`: Redux selection and search results in, `loadSelectedSkills` out, the site's dialogs and toasts for notices, and the HUD driving the view through its ref.

### Embedding in other apps
`packages/README.md` is the public guide for apps that add this repo as a git submodule: workspaces on `<submodule>/packages/*`, `transpilePackages`, Tailwind `@import`/`@source`, the asset sync, the provider, examples, the build-code contract and known limits. Keep it accurate when a package's public API, setup or assets change. The packages must work from such a host: they may not depend on the site (the boundary rules above), on files outside `packages/`, or on an install inside the submodule.

### Skill tree data: generated structure plus authored presentation
- `packages/core/src/constants/gameSkillData.json` is **generated** by `yarn import-skills` (`scripts/skill-data.mjs`). Never edit it by hand. It is the source of node membership (**stable string app IDs**), types, cartesian positions, base links (`base`, `baseAnchor`), costs, levels, game text values, `retired` IDs, and `edges`.
- `edges` are undirected `[low, high]` pairs. `buildSkillTree` in `packages/core/src/constants/Nodes.ts` expands each pair into adjacency on **both** endpoints, because unlocking works from either side, and it throws on unknown endpoints or on types without authored presentation.
- `packages/core/src/constants/LegacyNodes.ts` holds only app-owned presentation: type colors, icons/assets and fallback text, plus a per-node `tier`. A new type needs an entry here before an import can be applied. Import `SkillNodes`, `getMaxLevel` and `RETIRED_NODES` from `@enshrouded/core`.
- Node IDs are persisted in saved and shared builds. **Never renumber or reuse IDs.** `scripts/skill-data-mapping.json` holds `nodes` (game ID → app ID/type) and `retired` app IDs. The importer reads and writes `gameSkillData.json`, `LegacyNodes.ts` (read only) and `locales/<lang>/nodes.json` in `packages/core/src` (`CORE_PATHS` in the script), and imports into every locale folder there. Imports match by game ID and always write a diff to `.local/skill-data/` (`summary.md`, `report.json`, `changes.proposed.json`). Additions, removals, re-IDs, retypes and edge or base changes are refused on `--apply` until they are approved in `.local/skill-data/changes.json`. `scripts/skill-data-structure.test.mjs` tests this against a synthetic export (`scripts/fixtures/synthetic-export.mjs`); never run `--apply` with a synthetic export in the real checkout, because it overwrites real data.
- Game updates (export, preview, review, apply, verify) are run by the `enshrouded-game-update` skill in the sibling repo `../enshrouded-tools` (`.agents/skills/`, with a `.claude/skills/` wrapper), so start them from a session there. `docs/game-metadata-migration.md` describes the full import workflow and its known exception (Ranger stats). Read it before touching import or node data.

### Positioning
`packages/core/src/utils/nodePosition.ts` (`resolveNodePosition`) handles legacy `angle`/`distance` fields, `position: {kind:"polar"}` and `position: {kind:"cartesian", x, y}`. An explicit `position` wins over the legacy fields. +X points right and +Y points down, with the tree center as origin. Base nodes connect to the 198-unit core circle, or to an explicit `baseAnchor`.

### Text and localization
- The site's `public/locales/{en,fr}/common.json` holds its UI strings (next-i18next, `common` namespace only). Skill and tree text belongs to core: `packages/core/src/locales/{en,fr}/nodes.json` holds per-type text and `tree.json` the tree labels. Core reads them through its own private i18next instance (`text.ts`): `getSkillName`, `getSkillDescription`, `getSkillPerLevelLabel`, `getSkillText`, `getNodeName` and `getTreeLabelName` take the locale as an argument and work on the server and in any host. Imported game text (English and French) lives under each record's `game` key. A locale shows `game` text when the type's `gameTextLocales` lists it, otherwise its own translation; `skillTextPrefix` (`packages/core/src/utils/skillText.ts`) picks the record, and the tooltip, search, toasts and `?focus=` all go through the core text functions. A new locale needs a folder there and an entry in `skillTextResources`.
- `scripts/validate-translations.js` (run by `prebuild`, so a failure breaks the build) loads core's tree and interpolation through `jiti` and checks what each site locale actually shows: the zod schema (strict, no extra keys), an entry for every type in `LegacyNodes.ts`, and, for every type in the tree, a `name`, a `description` whose `{{placeholders}}` all have values at every level, and a per-level line in the locale's language (`perLevelLabel`; outside English the authored `perLevel.label` fallback is English, so it is an error). `tree.json` needs a label for every `TREE_LABELS` entry. For `common.json` and the React package's `locales/<lang>.json` it checks key and placeholder parity with `en`, every key the code references (literal `t()`/`uiText()`/`i18nKey`, and string literals naming a key in a known section; `src/` for the site, `packages/react/src/` for the package), and every value of keys built at runtime (the package's `biomes.<id>`). A new ``t(`prefix${...}`)`` prefix fails until it is listed under `families` (site) or `uiFamilies` (package) in the script. The importer only refuses `--apply` for a new type without a `description`; the build check covers the rest.
- Descriptions are i18next templates. Their numeric values come from node-type metadata: `gameValues`, `gameLevelValues` (indexed by purchased level) and `gamePerLevelValues`, plus the legacy `levelValues` and `perLevel`. `packages/core/src/utils/skillInterpolation.ts` resolves them. Core returns unescaped HTML; the React package's tooltip sanitizes it with DOMPurify before rendering.

### State and build sharing
- There is a single Redux slice, `src/redux/skills/skills.slice.ts`. It holds `selectedSkills` as an `{id: level}` map (legacy builds were `string[]`, which `normalizeToMap` handles), search results, flame level, unlocked biomes and player level. The slice is persisted to **sessionStorage** via redux-persist, with versioned migrations in the slice.
- A build's share code is `btoa(JSON.stringify(SkillBuild))`, owned by core (`packages/core/src/build.ts`): `selectionToBuild`, `encodeSkillBuild`, `decodeSkillBuild` (also reads the legacy `string[]` format), `parseSkillBuild` (JSON files) and `buildToSelection`. The format is frozen: `build.test.ts` pins real codes byte for byte, so never change how a code is written (add optional fields only). `BuildShareDialog` either places the code directly in `?code=`, or POSTs it to `/api/code`, which stores it in Mongo (`skill-planner.codes`) and returns an ObjectId used as `?shortCode=`.
- `pages/index.tsx` `getServerSideProps` resolves `shortCode`/`code`, plus `focus`. If Mongo is unset or can't connect, the page still renders without DB features (the `dbAvailable` prop) and `?code=` still loads; only `?shortCode=` needs the DB. An `ENOTFOUND` connection error renders nothing (`clusterStillProvisioning`). Every way of loading a build goes through `useLoadBuild`/`useApplySelection` (`src/hooks/useLoadBuild.ts`): share codes (`InitSkills.tsx`), JSON import (`HUD.tsx`) and a restored session on mount. These run `sanitizeSelection`, which drops retired IDs and skills disconnected from a base node and clamps levels to `maxLevel`, then toast what changed and warn about a different `treeContentHash`.
- `packages/core/src/constants/skillTreeVersion.ts` derives the tree's game build, update number and content-hash revision from the generated JSON. This tree version is separate from `APP_VERSION` (`src/constants/version.ts`, which `scripts/generate-version.js` generates from package.json).

### Selection rules
Selected nodes must stay connected to a `base: true` node. `getSelectableSkills` (unselected base nodes plus unselected neighbors of selected nodes) drives unlocking. When a node is refunded, `getSkillsToRemove` and `getSubGraphNodes` in `packages/core/src/selection.ts` find the selected nodes that would lose their path to a base node, and those are removed along with it. A `SkillBuild` stores `skills` together with `skillLevels`. The flame level's cap is `MAX_FLAME_LEVEL` (from the game data, in `constants/Biomes.ts`). Point budgets come from biomes and player level (`getMaxSkillPoints`, `getPointsUsed` and `fitsUnderHardCap` in `packages/core/src/points.ts`, `constants/Biomes.ts`; UI in `@enshrouded/react`'s `PointsPanel.tsx`), and stat totals come from core's `utils/stats.ts`.
